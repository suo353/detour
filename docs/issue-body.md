## 参赛项目名称

绕路 Detour：城市目的地探索智能体（长尾街区路线）

用户只说「我在武林广场，今晚 3 小时」，系统先剔除榜单上的热门点，再给出同一条街区内、全程步行的可执行路线。

## 旅行场景与目标用户

赛题方向：目的地探索（方向 8）。要回答的不是「帮我规划行程」，而是「这 3 小时怎么安排才不浪费」。

目标用户：在陌生或熟悉的城市里有 3 至 5 小时空档的人，例如出差间隙、周末半日、带朋友逛本地。他们不缺「去哪」的清单，缺的是一条现在就能走、不用打车、也不会拥挤的路线。

要解决的供给问题：飞猪 POI 库里大量小馆、老铺、书场、街区已经收在库内，有坐标、有简介、有跳转链接，但因为没进榜单，几乎不可能被看到。对杭州 10 个文化向类目做实测，87 个可去地点里有 52 个在平台榜单上没有名次，占 59.8%。

这个作品的重点不是再做一个行程规划器，而是把没进榜单的长尾供给重新纳入可推荐范围。

## 我做了什么

### 1. 把榜单排名当作负向信号

常规做法是拉取景点列表再排时间，候选池本身就是榜单，结果永远是那几个地方。绕路反过来：榜单排名非空的 POI 默认不进入路线，理由是上榜通常意味着排队和拥挤。

被剔除的点会单列成一节展示，用户可以核查「排除了什么」，而不是只听一句口号。

杭州夜游实测：点库共 78 个点，其中 19 个带榜单编号，清河坊街、南宋御街、小河直街、雷峰塔等全部被剔除。

### 2. 用地理聚类替代时间轴排点

先按 800 米步行半径做贪心聚类，优先取密度最高的一簇，再在簇内安排顺序。一条路线对应一个街区，而不是把一座城市的四个景点串成一条线。这样做的副产品是全程步行、不用打车、不用提前买票。

### 3. 四个主题是引擎的输入维度

同一座城市（杭州）、同一个出发点（武林广场）、同样 3 小时，只换主题，结果如下：

| 首条路线（每行一条，主题 · 三个主题各 3 条方案）                                              |
|:---------------------------------------------------------------------------------------------:|
| 夜游 · 武林夜市 → 浙江省文化馆小剧场 → ET PARK 酒吧（西湖店）                                 |
| 建筑 · 富义仓艺术中心 → 香积寺广场 → 妙等觉 → 大兜路历史文化街区                              |
| 非遗 · 中山公园-中山纪念亭 → 御座房 → 西泠印社 → 岳飞纪念馆                                   |
| 动漫 · 南山路一带手办、谷子、潮玩小店（点库按人群重建：手办、谷子、潮玩、漫展、电玩城、桌游） |

### 4. 引擎外置为脚本，模型只负责叙述

`explore.py` 为单文件、零第三方依赖，负责检索、打分、聚类、剔除榜单点、计算真实路网。模型负责把候选簇写成「几点到、待多久、怎么走、干什么、花多少」。

这样分工的原因有两点。其一，判断 80 多个 POI 两两距离是否小于 800 米，属于纯几何计算，交给脚本比交给模型更可靠，结果也可逐条核对。其二，每次运行需要 8 至 15 次检索，原始 JSON 的体量远超报告本身，直接交给模型既不利于复核，也无法保证同样的输入得到同样的输出。放进脚本后，候选集可以稳定复现，便于答辩时对照。

### 5. 三条输出约束

1. 不拼线：簇内点不够时不跨簇凑数，宁可只给两站，并在结果中标明。
2. 不编价：门票和酒店拿不到就写「无数据，出发前确认」，不填任何猜测价格。
3. 来源可追溯：每条答案附一行数据来源，例如「周边吃、看来源：随包或本地缓存 26 条，高德实时 4 条」，并说明哪部分没拿到、具体原因（如飞猪返回 HTTP 402，额度已用尽）、改用了什么。

- 百炼能力 / 模型：Managed Agent（云端托管长程任务），模型 DeepSeek-V4.1-Flash-1017。
- 调用方式：百炼控制台 → Managed Agent 智能体会话（agent_01M63PAJM4F40DRQVXNR58T3P3）；会话内由智能体调用 bash 工具执行技能包中的 scripts/explore.py。
- 链路位置：运行时链路。评委在会话里提问的每一轮，都是智能体在沙箱中实时执行 explore.py 并调用飞猪、高德接口；开发期我们只用同一套代码建点库与跑回归，没有把数据处理预先写死在答案里。
- 使用环节与输入输出：

| 环节                    | 输入                                    | 输出                                               |
|:------------------------:|:----------------------------------------:|:---------------------------------------------------:|
| 意图解析                | 「我在武林广场，今晚 3 小时，想走夜游」 | 城市、出发点、时长、主题四个槽位                   |
| 引擎检索（bash + 技能） | 四个槽位加主题关键词                    | JSON：候选簇、剔除的榜单点、每段真实步行距离与耗时 |
| 周边与酒店              | 站点坐标                                | 每站的吃、看推荐，以及按方案各 2 家酒店            |
| 成稿                    | 上述 JSON                               | 三条方案，每条一行「适合谁」，附路线图链接         |

- Skill 名称：自建技能 detour-engine，当前版本 V8.3，引擎为单文件 explore.py，系统提示词为 v190。随包内容包括 scripts/explore.py、data/themes（308 份城市与主题点库）、data/poi（232 份）、data/amenities（101 份城市吃喝与文保池）、data/snap（路网可达性网格）、map.html（离线地图页）。
- 凭据与脱敏：公开交付物（仓库与源码包）不含任何 API Key。引擎运行时读取环境变量 AMAP_KEY 与 FLYAI_API_KEY；两个变量都没有时会明确打印缺 Key 的提示，不会静默失败。线上演示用的 Key 由作者在百炼会话环境变量中私密注入，不随包、不入库。
- MCP：Amap Maps 高德地图，官方 MCP，15 个接口全启用，用于地理编码、真实步行路径兜底、天气和周边补数。它不参与「发现或替换地点」，因为高德自带热门排序，与本产品的取点立场相反。
- 其他工具与技术栈：
  - Python 3.11，沙箱内运行，零第三方依赖。
  - 飞猪 @fly-ai/flyai-cli，用到 search-poi、search-hotel、ai-search，技能内自动懒安装。
  - OSRM 步行路网，处理 GCJ-02 与 WGS-84 互转，折线用 Ramer-Douglas-Peucker 抽稀。
  - Leaflet 静态地图页，托管于 GitHub Pages，数据全部写在 URL 参数里，无后端。

- 体验条件：飞猪首次登录赠送 5000 次调用、用完后每天 100 次；随包点库命中时，一次问答只需 0 至 2 次调用，冷门城市约 8 至 15 次。高德关键字与周边搜索共用一个每月 5000 次的免费额度，点库已随包，日常问答基本不消耗搜索额度；高德另需自备 Key 才能查地理编码与步行兜底。

本地复现：

```bash
# 1) 解压 detour-agent-src-lite.zip，安装飞猪 CLI
npm i -g @fly-ai/flyai-cli --registry=https://registry.npmmirror.com

# 2) 注入自己的 Key（公开交付物不含 Key；也可写进 skill-package-engine/scripts/amap_key.txt 与 flyai_key.txt）
export AMAP_KEY=你的高德Web服务Key
export FLYAI_API_KEY=你的飞猪Key

# 3) 跑一条
cd detour
python3 explore.py --city 杭州 --theme 夜游 --hours 3 \
  --anchor 武林广场 --auto-order --brief

# 4) 输出包含三条方案及其路线图 URL，点开即为该街区

```

接入百炼共 6 步：新建 Managed Agent（模型 DeepSeek-V4.1-Flash-1017，启用 bash、read、write），粘贴 prompts/system-prompt.md 中 ==== 之间的正文，添加 MCP「Amap Maps 高德地图」，上传并添加技能 detour-engine（zip），建会话（环境变量留空），然后问「我在杭州武林广场，今晚 3 小时，想走夜游」。

需要注意，修改提示词或更换技能后，已存在的会话仍绑定旧快照，必须新建会话才会生效。

## 踩坑记录（可选）

1. Trial limit reached 与 Total usage limit reached 表示额度用尽，不是限流。飞猪 AI 开放平台的规则是首次登录赠送 5000 次调用、永久有效，用完后每天 100 次，控制台没有充值入口。所以演示前固定用已预热城市的主题，随包点库命中时一次问答只需 0 至 2 次调用。
2. 「额度用尽」曾被我们的代码误判。早期引擎对整段 JSON 做包含判断，POI 经纬度里恰好出现 402、451 等数字时就会误判为风控并熔断整轮。改为只匹配完整短语（risk control、total usage limit、trial limit），并且只解析 data.error 与 data.code 之后，「控制台还有 96 次却说额度用尽」的情况不再出现。
3. 高德免费额度按服务组统计。关键字搜索、周边搜索、多边形搜索、ID 查询、输入提示共用一个 5000 次每月额度（个人认证开发者）。本项目为构建随包点库批量建库时曾用满该额度，现在点库随包，日常问答的搜索调用为 0 至 2 次。高德流量包需先购买技术服务许可基础版，价格为 50000 元每年，所以本项目在设计上不依赖高德搜索额度。
4. 坐标系。飞猪 POI 与高德瓦片为 GCJ-02，OSM 路网为 WGS-84，杭州一带偏差约 519 米。请求路网前后各转换一次；折线用 Ramer-Douglas-Peucker 抽稀，3 米容差，否则 1.6 公里的线路只剩 60 个点，会出现约 150 米的直线段，看上去像斜穿街区。
5. 同址去重。杭州运河游船与武林门码头坐标只差 2.4 米，不合并会让「簇内有 3 个点」变成假象，所以聚类前先做 60 米去重。
6. 空结果不能写入缓存。额度耗尽那几天，空结果被写进单站缓存并保留 3 天，之后一直命中空缓存，表现为西湖周边也查不到数据。现在改为只有非空结果才写入，并把缓存改为固定文件名加 30 天有效期。
7. 百炼的边界情况。技能处于「安全扫描中」时保存智能体会静默失败；技能刚更新的一段时间内，直接更换版本会被保留旧版本，需先删除引擎保存一版，再添加新版本并保存。
8. 会话是快照。智能体、技能、提示词都在会话创建时固化，改完不生效的错觉就是这么来的，所以验证时一律新建会话。
9. 脏数据需要清理。主题点库曾混入「仓库」「公司」这类泛匹配结果，以及陵园、烈士墓一类不适合步行线的点位。现在有名字黑白名单，并做过一次全量清理，共剔除 336 条。
10. 演示预算。飞猪每天 100 次调用，一次冷跑需要 4 至 12 次，热跑 0 至 2 次。所以演示路线先在本地跑好，录屏时只点链接。
11. 凭据管理。早期版本为了演示方便，把 Key 写进技能包的 scripts/*.txt，并在测试报告里贴过明文。收到提醒后已做三件事：从公开交付物中删除全部 Key 与明文引用，改为环境变量注入；轮换已暴露的 Key；在 README 与本文档中补上自备配置说明。仓库历史里若仍能检索到旧串，旧 Key 已作废。
